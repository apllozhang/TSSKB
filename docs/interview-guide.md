# 阿里高级工程师面试讲解材料

这份材料用于解释工程判断和证据，不承诺职级或薪酬结果。重点是让面试官能从仓库中验证你的设计，而不是只听概念。

## 30 秒项目介绍

“这是一个 ALE 内部技术培训门户。原版本能生成站点，但 65 门课程、模板、CSS、搜索和发布都集中在约 1500 行脚本里，缺少测试和安全发布。我保留静态架构，因为它符合只读、高读取低写入的业务模型；平台化改造发生在内容契约、增量构建、搜索分片、CI、可观测性和原子发布层。现在 65 门课程和 369 个知识单元由 schema 治理，661 个页面和 24,000 多个引用会被自动校验，发布支持版本目录、健康检查和失败回滚。”

## 高频问题与回答骨架

### 为什么不引入数据库和微服务？

先讲业务比：内容变更频率低、访问频率高、没有用户状态。数据库会增加备份、迁移、权限、可用性和故障面，但不能改善主要用户价值。当前用 Git 作为事实源、CI 做治理、静态文件做运行态。如果后续有非技术运营和审批需求，再通过 ADR 评估 Headless CMS；如果有学习进度，再拆独立状态服务。

### 单体脚本是怎样拆的？

不是按文件数量机械拆分，而是按变化原因拆：模型因业务合同变化，loader 因输入格式变化，renderer 因页面表现变化，search 因容量/检索策略变化，deploy 因运行风险变化。`pipeline.py` 只编排这些边界。原脚本保留在 `tools/legacy`，根命令成为兼容包装器。

### 怎么证明构建可复现？

输入由稳定 JSON 和文件 SHA-256 计算，输出 manifest 对每个文件计算 SHA-256；构建时间单独写 metrics，不进入内容摘要。CI 构建两次并比较 input/output digest。增量测试还会证明无变化构建与完整构建的 output digest 和 provenance 一致。

### 搜索为什么分片？

1.x 第一次搜索下载 2.48 MB 原始/758 KB gzip 的单文件。2.x 首次只加载 gzip 约 40 KB 的标题索引，用标题和章节定位分类，再加载候选正文分片；最大正文分片约 450 KB。正文关键词无法定位时才回退全部分片。CI 对总量和单资产同时设预算。

### 发布为什么安全？

旧脚本是 `rm -rf` 后上传，任何中断都会留下空站。新流程上传到不可变 `releases/<id>`，核验 release manifest，再用软链接原子切换。切换后检查首页、搜索、代表课程和品牌资产；失败立即恢复 previous。手工回滚的目标若未通过健康检查，也会补偿恢复回滚前版本。SSH 拒绝未知主机。代码已用 fake transport 验证状态顺序和补偿分支，线上仍需凭据与授权才执行。

### 如果内容翻倍会怎样？

当前 3,929 个条目、搜索 gzip 0.83 MB。按当前平均值，5,000 条接近原始总预算，10,000 条需要压缩字段或调整策略，20,000 条应评估预构建倒排索引。分片器会自动把大分类拆成多个约 450 KB 文件，单分类增长不会重新形成巨型文件。

### 安全怎么考虑？

配置字段统一自动转义，Jinja2 使用 StrictUndefined；Markdown 只接受 Git 受控输入。部署凭据不入仓库，SSH 主机密钥必须验证。运行时无数据库、会话和动态执行，Nginx 配置增加 CSP、MIME 嗅探、Referrer Policy 和权限策略。

## 面试演示顺序（8 分钟）

1. 先打开真实门户，展示业务规模与 ALE UI；
2. 打开 `content/catalog.json` 和 schema，演示新增课程不改 Python；
3. 故意写一个不存在的 skill，运行 validate，展示定位错误（演示后还原）；
4. 运行完整构建和 metrics，解释搜索分片与预算；
5. 打开 manifest，展示 input/output digest 和 provenance；
6. 运行 deploy/rollback dry-run，解释不可变发布状态机；
7. 展示 CI 和失败健康检查自动回滚测试；
8. 用 ADR 回答“为什么没上数据库/微服务”。

## 不要过度声称

- 本地测试通过不等于生产可用性已经达到 99.9%；
- dry-run 不等于真实服务器发布成功；
- 静态分片搜索不是大规模检索引擎；
- P7 设计证据提高面试说服力，但职级还取决于业务影响、组织协作和面试表现。
