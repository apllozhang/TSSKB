AOS Access Guardian 802.1X/UNP 分类流水线与 LLDP-MED 话机

R — 原文 (Reading)

"802.1X enabled? → Pass? → RADIUS Filter-Id → UNP Profile; Fail → Classification Rules → UNP Profile; No Auth → Default UNP Profile; Block ... Users are moved to a specific profile when RADIUS server is not available. Auth Server Down Timeout = 60"

— ALE Training, Access Guardian (220 p646, p653, p661)

I — 方法论骨架 (Interpretation)

端口上线一个终端后，交换机沿一条固定决策链决定它进哪个 UNP profile： 1. 端口开了 802.1X 且有 supplicant → 认证通过 → 用 RADIUS Access-Accept 里的 Filter-Id（= UNP 名）套 profile；无/无效 Filter-Id → 落 pass-alternate profile； 2. 无 supplicant（哑终端）→ MAC 认证分支，同构； 3. 认证不开或失败 → 本地分类规则（Port > Domain > MAC > MAC-OUI > MAC range > LLDP > Auth-type > IP > VLAN tag；Extended > Binding > Simple 规则）； 4. 兜底 → 端口 default-profile（通常是受限/隔离 VLAN）；RADIUS 不可达 → auth-server-down profile（默认 60s 重试）；全部无效 → Block。

每个 UNP = VLAN 映射 + policy list（ACL/QoS）+ location/period 策略的容器。话机场景：LLDP-MED network-policy TLV 下发 voice VLAN+802.1p+DSCP，话机据此打 tag，交换机 mobile-tag profile + trust-tag 分类收流——mobile 口不支持静态 802.1Q tag。

A1 — 书中的应用 (Past Application)

案例 1: Access Guardian 802.1X/MAC 认证完整部署（c28, 220 p648-661）

  • 问题: 员工 PC 与哑终端都要按身份进不同 VLAN 并限 FTP。
  • 方法论的使用: aaa radius-server + aaa authentication 802.1x/mac → 建 VLAN + UNP profile（corporate/def_unp）→ port-template（802.1x-authentication + pass-alternate corporate）→ unp port port-type bridge + default-profile → policy list deny_employees 挂到 unp profile（qos-policy-list + location + period）→ unp auth-server-down profile 兜底。
  • 结论: 认证通过由 Filter-Id 或 pass-alternate 决定 profile，失败落 def_unp（隔离 VLAN）。
  • 结果: show unp user port 1/1/1 可见终端、profile、VLAN 归属，策略生效。

案例 2: LLDP-MED 话机零配置上线（c29, 220 p677-685）

  • 问题: IP 话机即插即用进语音 VLAN 151。
  • 方法论的使用: unp profile "voip-temp" mobile-tag + map vlan 151 → unp classification lldp med-endpoint ip-phone profile1 voip-temp → lldp network-policy 1 application voice vlan 151 l2-priority 5 dscp 46 + lldp chassis med network-policy 1 → 端口 tlv med network-policy enable。
  • 结论: 话机从 TLV 学到 VLAN/优先级并打 tag，交换机 trust-tag 分类进 151。
  • 结果: show lldp remote-system med inventory 看到 IP Touch 8068 详情，语音流自动带 802.1p 5。

案例 3: 无认证纯分类动态 VLAN（c06, 220 p142-145）

  • 问题: 不部署 RADIUS，按 MAC 段自动分 VLAN。
  • 方法论的使用: unp classification-rule rule1 mac-address-range ... → profile corporate；端口 default-profile 指向隔离 VLAN。
  • 结论: 分类规则在认证禁用时同样驱动动态 VLAN。
  • 结果: 终端按 MAC 段落入业务/隔离 VLAN。

A2 — 触发场景 (Future Trigger) ★

用户会在什么情境下需要这个 skill?

  1. 规划接入口策略：员工 802.1X、打印机/摄像头 MAC 认证、访客落受限 VLAN，问"认证失败/服务器挂了终端去哪"。
  2. 配置 RADIUS 下发 Filter-Id 或 pass-alternate，用户/哑终端混合口怎么设计。
  3. IP 话机零配置部署：LLDP-MED 下发语音 VLAN/QoS，话机+PC 共口。
  4. 排查"终端进了错误 VLAN / 认证失败但还能上网 / 话机不打 tag"。

语言信号 (用户的话里出现这些就应激活)

  • "802.1X 认证 / dot1x / MAC 认证 / NAC / Filter-Id / pass-alternate"
  • "UNP / classification rule / 动态 VLAN 按终端 / default profile"
  • "话机自动进语音 VLAN / LLDP-MED / mobile-tag / voice VLAN 下发"
  • "RADIUS 挂了端口怎么办 / auth server down"

与相邻 skill 的区分

  • 与 ov-wired-auth-config 的区别: 那是 OmniVista Cirrus/Terra 上 Stellar AP/OmniSwitch 的 AAA Server Profile 四步链；本 skill 是交换机本地 CLI 的 Access Guardian/UNP 体系。
  • 与 aos-l2-security 的区别: 那是端口级防攻击特性（ARP/风暴/LPS）；本 skill 是身份/分类驱动的动态接入策略。
  • 与 aos-vlan-mvrp 的区别: 那是静态 VLAN/trunk/MVRP 传播；本 skill 按终端身份动态选 VLAN。

E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

  1. 判定分支: 确认需求是认证型（802.1X/MAC）还是纯分类型（无 RADIUS）还是话机型（LLDP-MED）。
  2. 完成标准: 明确说出走哪条分支及其判定链位置。
  3. 基础件先行: 建 VLAN（含隔离 VLAN）+ UNP profile 并 map vlan；端口 port-type bridge + default-profile。
  4. 完成标准: show unp profile 列出 profile-VLAN 映射。
  5. 认证型配置链（Access Guardian 七步）: aaa radius-server（可 aaa profile 打包 802.1x/mac 双认证 + ip service source-ip loopback0 radius）→ port-template（802.1x-authentication + pass-alternate）→ 应用到 UNP 端口 → unp auth-server-down profile + timeout 60。
  6. 完成标准: show aaa device-authentication 802.1x 正常，RADIUS 侧 Filter-Id=UNP 名已核对。
  7. 话机型配置链: mobile-tag profile + lldp med-endpoint 分类规则 + network-policy（voice vlan + l2-priority 5 + dscp 46）+ 端口 med TLV enable。
  8. 完成标准: show lldp remote-system med 可见话机 inventory 且 VLAN 正确。
  9. 验证与排障: show unp user details port X 查终端落点；不对则按判定链回溯（Filter-Id→pass-alternate→分类规则→default）；分类不中时核对规则优先级（Port>Domain>MAC>OUI>range>LLDP>Auth>IP>tag；Extended>Binding>Simple）。
  10. 完成标准: 每个测试终端落入预期 profile/VLAN，兜底路径（认证失败、server down）均演练过。

B — 边界 (Boundary) ★

不要在以下情况使用此 skill

  • OmniVista 云侧有线认证（AAA Server Profile→Access Auth Profile→Access Policy 链）→ ov-wired-auth-config。
  • 无线 SSID/PSK 选型、漫游 → ov-ssid-psk-selection / ov-roaming-troubleshoot。
  • 管理员登录 AAA/SSH 加固 → aos-switch-access-mgmt；那是管理面不是数据面准入。

作者在书中警告的失败模式

  • ce35: 认证禁用/失败时端口不会关闭，而是回落 UNP 分类规则（或 Restricted profile）——"没认证就没策略"是错觉，安全预期必须按兜底 profile 设计。
  • ce23: mobile 端口不支持静态 802.1Q tag；话机 tagged 流量必须走 unp profile mobile-tag，否则被丢或落错 VLAN。
  • ce35(后半): PVLAN 下 UNP 口的 isolated/community 角色由首个学到的 MAC 决定；首 MAC 属普通 VLAN 则该口永远无法成为隔离/社区口。
  • p65: RADIUS 默认 retransmit 3 / timeout 2s / auth 1812 acct 1813；server-down 默认 60s 重试，恢复后自动重认证。

作者的盲点 / 时代局限

  • 教材基于 AOS 8.9R4~8.10R4，R9 命令可能变化；Filter-Id 机制仅覆盖 ALE 私有语义，与 Cisco/HP 的 dynamic VLAN 属性不通用。

容易混淆的邻近方法论

  • UNP 分类 ≠ MVRP 动态 VLAN（协议驱动 vs 终端身份驱动）。
  • Access Guardian ≠ OmniVista 有线认证（CLI 本地 vs 云平台）。
