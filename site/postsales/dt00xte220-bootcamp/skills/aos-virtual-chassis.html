aos-virtual-chassis

SKILL 来源页码: 220 p101-123 (Virtual Chassis), p49 (EMP dongle)

Virtual Chassis：选举 / 组建 / 脑裂防护 / ISSU / 同步

R — 原文 (Reading)

"Master/Slave election based on virtual chassis protocol (ISIS-VC): Highest chassis priority value / Longest chassis uptime (if difference >10 mn) / Smallest Chassis ID value / Smallest chassis MAC address" (220 p107) "Failures on VFL links cause potential MAC/IP duplication... The former Slave chassis will shutdown all its front-panel user ports" (220 p111-112)

— ALE Training, OmniSwitch LAN R8 Bootcamp Ed23, p107 / p111-112

I — 方法论骨架 (Interpretation)

VC 把多台物理交换机虚拟成单一管理/转发实体，四条主线：

  1. 选举判定链（先命中先赢）: 最高 chassis priority（0-255，想让谁当 Master 就设最高，如 200）→ 最长 uptime（差距 >10 分钟才计，防抖）→ 最小 Chassis ID → 最小 chassis MAC（兜底确定性）。附带规则：原 Master 恢复后不触发重选，新 Master 保留角色。改 chassis-id/priority 后必须 reload 才生效。
  2. 组建路径: 开机查 vcsetup.cfg——不存在（出厂首启）走 Auto-VC（auto VFL 端口探测 + 自动 Chassis ID，两端都是 auto VFL 口才协商成 VFL；各机型默认 auto-VFL 口位不同，9900 仅静态）；存在则按配置进入。手工四步：分配 chassis ID（VC 内唯一）→ Group ID + Priority（全网同 group）→ 配 VFL（自动或静态）→ 从含 vcsetup.cfg/vcboot.cfg 的目录重启。
  3. 脑裂（split chassis）防护双机制: VFL 全断 → 原 Slave 可能变伪主，造成 MAC/IP 重复。带外：EMP 口跑 RCD（IP 优先级 CMM NVRAM IP > EMP IP），检测到分裂后原 Slave 关闭所有前面板口、状态置 Split-Topology；带内：需一台上下游 helper 交换机跑 VC Split Protocol，推荐每个 VC 成员至少一口加入到 helper 的 VCSP LAG。VFL 恢复后原 Slave 重启并以 Slave 重新加入。
  4. ISSU 与同步: ISSU 把新镜像+vcsetup.cfg+vcboot.cfg 上传新目录 → issu 命令 → 文件自动复制到所有 Slave → Slave 按 chassis ID 从低到高逐台重启 → Master 最后。配置同步三级：RAM running → 各成员 certified；write memory 只同步 running，copy running certified / write memory flash-synchro 才把 certified 层同步全部成员；show running-directory 见 "Flash Between CMMs: NOT SYNCHRONIZED" 即成员 flash 落后。一致性硬约束：chassis type、group、hello interval、control VLAN、license 必须一致（show virtual-chassis consistency 带 * 项）。无 EMP 口机型 VC 内每台都插 USB-to-Ethernet dongle。

A1 — 书中的应用 (Past Application)

案例 1: VC 部署与同步验证 (220 p113-122, c04)

  • 问题: 两台机组 VC 后配置不一致、成员访问困难。
  • 方法论的使用: ssh-chassis admin@2 直达任意成员 CLI；show running-directory 发现 CERTIFY NEEDED 与 Flash Between CMMs: NOT SYNCHRONIZED → write memory flash-synchro 一步完成保存+成员同步。
  • 结论: VC 的配置"定版"必须落到所有成员的 certified 层。
  • 结果: show 变为 SYNCHRONIZED，教材把该检查固化为 VC 变更收尾。

案例 2: 脑裂防护设计 (220 p111-112, ce12)

  • 问题: 跨机柜 VC 的 VFL 有全部断开风险。
  • 方法论的使用: 带外 EMP 跑 RCD（优先 NVRAM 中 CMM IP）+ 带内为每成员配 1 口到 helper 交换机的 VCSP LAG。
  • 结论: 无 helper 且 EMP 不通时脑裂无法自愈——设计期必须二选一落地。
  • 结果: 伪主关闭前面板口（状态 Split-Topology），杜绝重复 MAC/IP。

案例 3: ISSU 在线升级 (220 p113, f04)

  • 问题: 双成员 VC 不能整机停机升级。
  • 方法论的使用: 新目录 issu_dir 放 code+vcsetup.cfg+vcboot.cfg → issu 命令 → Slave 按 chassis ID 升序逐台 reload → Master(Chassis ID 1) 最后。
  • 结论: 逐成员重启换取整机业务不中断。
  • 结果: 教材标准升级窗口流程。

A2 — 触发场景 (Future Trigger) ★

用户会在什么情境下需要这个 skill?

  1. 规划/组建堆叠：选 Master、分配 chassis-id/group/priority、规划 VFL 口。
  2. Master 漂移/选举不符合预期排查；改了 priority 不生效。
  3. VFL 断裂后的脑裂处置与事前防护（RCD/VCSP helper 设计）。
  4. VC 升级窗口（ISSU）或成员配置不同步（NOT SYNCHRONIZED）。

语言信号 (用户的话里出现这些就应激活)

  • "堆叠 脑裂怎么防 / split-topology"
  • "谁当 Master / chassis priority / 选举"
  • "VFL / auto VFL 端口 / vcsetup.cfg"
  • "ISSU / issu_dir / VC 升级"
  • "flash-synchro / NOT SYNCHRONIZED / ssh-chassis"

与相邻 skill 的区分

  • 与 aos-switch-access-mgmt 的区别: 那边管单机 RAM→working→certified 模型；本 skill 的同步是"多成员 certified 层面"（flash-synchro），单机语义只作引用不展开。
  • 与 aos-lag-stp 的区别: VC 是设备级合一（对外一个 IP/MAC/一张表）；LAG/STP/DHL 是独立设备间链路冗余。"VC+LAG 双归"方案里 VC 部分归本 skill。
  • 与 aos-diagnostics-ops 的区别: 单机软件镜像升级六步法归那边；本 skill 只在"VC 整体不中断升级（ISSU）"时接管。

E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

  1. 判定任务类型（组建 / 选举排查 / 脑裂 / ISSU / 同步）
  2. 完成标准: 四选一明确，并给出对应页码锚点。
  3. 组建路径: 先问 vcsetup.cfg 是否存在——出厂首启走 Auto-VC（按机型核对 auto-VFL 口位表），否则手工四步（chassis ID 唯一 / group 一致 / priority 定主 / VFL 配置后从含 vcsetup.cfg 目录重启）
  4. 完成标准: 参数表齐全；提醒"chassis-id 全 VC 唯一、group 全 VC 相同、改 ID/priority 必须 reload"。
  5. 选举排查: 按判定链逐项比对（priority → uptime>10min → chassis ID → MAC）
  6. 完成标准: 能解释当前 Master 为何是他；原 Master 恢复不重选的规则已告知。
  7. 判停条件: 若 show virtual-chassis consistency 有带 * 不一致项，先修一致性。
  8. 脑裂处置/设计: 查 chassis 状态是否 Split-Topology → 带外核对 EMP/RCD（CMM NVRAM IP 优先）→ 带外不可用则核对 helper 交换机 + VCSP LAG（每成员 ≥1 口）→ VFL 恢复后原 Slave 自动重启重入
  9. 完成标准: 给出事前防护清单（含 USB dongle 要求）与事后恢复预期。
  10. ISSU: 上传 code+vcsetup.cfg+vcboot.cfg 到新目录 → issu 命令 → 确认 Slave 按 chassis ID 低到高逐台 reload
  11. 完成标准: 说明窗口内不要叠加其它配置变更。
  12. 同步收尾: show running-directory → NOT SYNCHRONIZED 则 copy running certified 或 write memory flash-synchro
  13. 完成标准: 状态变 SYNCHRONIZED；警告 write memory 弹 "Chassis X missing" 时确认 Y 会永久清除该成员配置——必须先核实拓扑。

B — 边界 (Boundary) ★

不要在以下情况使用此 skill

  • 单机配置保存/certify/回滚与 Lightning Config——用 aos-switch-access-mgmt。
  • 链路聚合、STP/MSTP、DHL、ERP 冗余——用 aos-lag-stp。
  • 单机（非 VC）镜像升级、诊断工具——用 aos-diagnostics-ops。

作者在书中警告的失败模式

  • ce12: VFL 全断 → 双主带来 MAC/IP 重复；带外 RCD 让伪主关所有前面板口；带内依赖 helper 交换机的 VC Split Protocol（建议每成员一口入 VCSP LAG）；无 helper 且 EMP 不通则脑裂无法自愈。
  • ce13: 改 chassis-id/priority 不 reload 不生效；拓扑成员缺失时 write memory 确认 Y 会永久清除该成员配置；手工编辑 vcboot.cfg 的 [SAVED INFO] 区段会破坏 VC 状态。
  • 另（p132/p49）: 一致性强制项不一致影响 chassis 状态；无 EMP 口机型 VC 每台都要 USB dongle，否则 EMP 功能不正常。

作者的盲点 / 时代局限

  • 教材以双成员 VC 实验为主，多成员（>2）场景的 VFL 带宽规划与选举细节未展开。
  • Auto-VC 与 Auto-Fabric（LLDP 自动建 VC）边界在本书两处出现，现场需区分"出厂自动"与"手工 vcsetup.cfg"两条路径。

容易混淆的邻近方法论

  • VC（设备合一，防设备故障）vs LAG（链路合一，防链路故障）vs DHL（双归属，防对端设备故障）。
  • VCSP LAG（脑裂检测用途，指向 helper）vs 普通 VCSP（跨机箱聚合）——目的不同。
