aos-diagnostics-ops

SKILL 来源页码: Diagnostics (p169-222) / SLB & Upgrade (p1041-1070)

诊断工具箱 / PoE / SLB / 软件升级

R — 原文 (Reading)

"swlog appid ospf_0 subapp hello level debug3 … Up to 8 Swlog logs files … Stores 100 most recent commands" (p172-192)

"Analyse Requirements on the release note / FTP the Upgrade Files to the Switch / Upgrade the image file / Verify the Software Upgrade / Certify the Software Upgrade / Upgrade uboot and/or FPGA if mandatory."

— OmniSwitch LAN R8 Bootcamp Ed23, Diagnostics & Upgrade, p172-192, p1065-1069

I — 方法论骨架 (Interpretation)

售后排障有固定工具梯队，按"侵入性从低到高"选用：

日志先行：swlog 三路输出（console/flash/syslog，syslog 最多 12 台、需 Loopback0 做源），文件默认 1250KB、8 个轮转 + 40 个归档；按 swlog appid <app> subapp <n> level debug3 精确定位子系统（OSPF 邻居不上先看 HELLO 子模块）；Readable Events 用 level event + show log events。command-log 记录最近 100 条命令含用户/IP/结果（启用中不可删），是"谁改了什么"的取证入口。

流量可视化：port-mirroring 抓包到分析口（与 monitoring 同口互斥）；port-monitoring 存 Sniffer 格式文件；RMON 探针/告警看计数器；sFlow 三件组装——receiver 指采集器（源地址建议 ip service source-ip Loopback0 sflow）、每接口一个 sampler（采样率）+ 一个 poller（计数器间隔）。show health 看 CPU/内存即时与 1min/1hr/1day 均值。

PoE：端口默认 disabled、优先级 low；预算不足先断 low 再 high，critical 保到最后——重要设备（摄像头/话机）设 critical。capacitor-detection 仅用于 legacy 话机且不兼容 802.3af。delayed-start（120-600s）与 FPoE/PPoE 互斥且必须 write memory。

SLB：VIP 必须与服务器同网段（proxy-ARP 兜底）；每机 16 cluster、WRR 总权重 ≤32、weight 0 = 备份机（主全挂才接管）；服务器 loopback 装 VIP（Windows weakhost / Linux arp_ignore）；每机 20 个 probe，状态机 Disabled→Discovery→In Service→Retrying→No Answer/Link Down。

升级六步法：读 release note（内存/UBoot/FPGA 要求）→ FTP 镜像到 running 目录 → reload from working no rollback-timeout → show version/microcode 验证 → 稳定后 copy running certified 固化 → 按需 update uboot/fpga-cpld。安全网：certify 前出问题可回退原 certified 版本。

A1 — 书中的应用 (Past Application)

案例 1: OSPF 邻居不上定位（c07）

  • 问题: 邻居起不来但无直观报错。
  • 方法论的使用: swlog appid ospf_0 subapp hello level debug3 只调 HELLO 子模块到 debug3，show log swlog | grep ospf 过滤。
  • 结论: 分子系统调级别比全局 debug 更快且不冲击 CPU。
  • 结果: 日志直接暴露 Hello 参数/网段不匹配点。

案例 2: 升级窗口执行（c42/f05）

  • 问题: 生产交换机升级 AOS 版本，要求可回退。
  • 方法论的使用: 六步法顺序执行，certify 前保持回退能力；release note 要求时补 update uboot cmm all file ... 与 update fpga-cpld。
  • 结论: certified/running 双目录是 AOS 的回退机制核心。
  • 结果: 升级后网络稳定，copy running certified 固化；异常场景演示回滚到原 certified 版本。

A2 — 触发场景 (Future Trigger) ★

用户会在什么情境下需要这个 skill?

  1. 故障排查第一入口：不知道先看什么日志、怎么抓包、怎么查 CPU/内存。
  2. 升级窗口：执行版本升级、uboot/FPGA 刷新，或升级后异常要回退。
  3. PoE 掉电/预算不足排查、AP/摄像头供电规划；服务器负载均衡（VIP/权重/备份机/健康探测）部署。

语言信号 (用户的话里出现这些就应激活)

  • "swlog / show log / debug 哪个级别 / command-log"
  • "port mirroring / sFlow / RMON / 抓包 / show health CPU 高"
  • "升级失败怎么回退 / certified / release note / uboot FPGA"
  • "PoE 断电 / 优先级 critical / 功率预算 / delayed-start"
  • "SLB / VIP / 负载均衡 / 备份服务器 weight 0"

与相邻 skill 的区分

  • 与各协议 skill 的区别: 本 skill 提供"用什么工具看"；日志定位到 OSPF/BGP/SPB 协议本身问题后转 aos-igp-routing/aos-bgp-vrf/aos-spb-fabric。
  • 与 aos-switch-access-mgmt 的区别: 交换机开局/管理面（账户、WORKING/CERTIFIED 目录概念、管理接入）走该 skill；本 skill 是排障工具、PoE/SLB/升级的操作方法论。

E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

  1. 建立诊断基线
  2. 指引用户收集：show health（CPU/内存趋势）、show log swlog 按子系统过滤、必要时 swlog appid <app> subapp <n> level debug3 精调、show command-log 回溯变更。
  3. 完成标准: 拿到至少一项指向具体子系统/时间点的证据。

  4. 判停条件: 若需逐包分析，跳步骤 2。

  5. 选择流量观测手段

  6. 计数器级用 RMON/show 接口计数；采样级用 sFlow（receiver/sampler/poller 三件，源地址 Loopback0）；逐包级用 port-mirroring 到分析口（提醒与 monitoring 同口互斥）。

  7. 完成标准: 给出与问题粒度匹配的工具及完整配置片段。

  8. PoE/SLB 处置（如属此两类）

  9. PoE：show lanpower slot 核预算 → 重要端口 priority critical → 涉及 delayed-start 时警告 FPoE/PPoE 失效与 write memory（ce36）。SLB：核对 VIP 同网段、WRR 权重 ≤32、备份机 weight 0、probe 配置与状态机。

  10. 完成标准: 供电/分发行为可解释且配置满足全部硬约束。

  11. 升级窗口执行

  12. 按六步法输出：release note 核对（内存/uboot/FPGA）→ FTP 上传 → reload from working no rollback-timeout → show version/microcode 验证 → 观察 24h 后 copy running certified → 按需 update uboot/fpga-cpld；明确"certify 之前都可回退"。
  13. 完成标准: 步骤顺序正确、验证命令与回退路径均已给出。

B — 边界 (Boundary) ★

不要在以下情况使用此 skill

  • 日志已指向具体协议故障（OSPF 邻居、BGP 策略、SPB 服务）——转对应协议 skill，本 skill 只负责"观测到证据"。
  • 交换机开局/账号/目录结构管理等管理面问题——用 aos-switch-access-mgmt。

作者在书中警告的失败模式

  • PoE delayed-start 代价（ce36）: 启用后 FPoE/PPoE 失效（断电不断供能力丢失）、必须先启 lanpower 且忘了 write memory 则重启不生效——对断电需立即恢复的摄像头/门禁是功能性回退。
  • 端口功能互斥（p107）: monitoring 与 mirroring 同口禁用；加 LAG 前须清既有 VLAN/镜像配置——报 "please remove other configuration" 时按互斥清单反查。
  • 升级顺序: 跳过 release note 直接刷镜像，可能因内存/uboot 不满足而变砖；未验证即 certify 丢失回退能力。

作者的盲点 / 时代局限

  • 工具规格（8 个 swlog 文件、100 条 command-log、12 台 syslog、20 个 probe）随版本演进，现场以对应版本配置指南为准；VC 堆叠场景的 ISSU 升级另有流程（见 c04，不在本 skill 范围）。

容易混淆的邻近方法论

  • mirroring vs monitoring：前者实时复制到目的口供外接分析；后者把捕获存成 Sniffer 文件。
  • running vs certified：reload 从 running 加载，certified 是固化后的出厂级安全网，二者是回退机制的根基。
