ov-wips-rogue-policy

SKILL 来源页码: WIPS, p381-390

WIPS 三分类与 Rogue 策略（OmniVista 无线入侵防护）

R — 原文 (Reading)

"Interfering AP: Any other APs discovered over the air... Rogue AP: Based on the Rogue AP Policy... Friendly AP is not reported as Interfering or Rogue"（p384） "Signal Strength Threshold... Default: –70 dbm; Range -50 to -90 dbm"（p385）

— ALE Training, WIPS (p381-390)

I — 方法论骨架 (Interpretation)

WIPS 是一个"默认宽松、逐级升级"的分类决策模型：

  1. 三分类基线：空中发现的一切外部 AP（本 OVC 管理的除外）默认归为 Interfering（仅干扰，不上纲）；命中 Rogue Policy 任一条才升级为 Rogue；手工或按 OUI（默认含 ALE OUI）标记为 Friendly 的不再上报。
  2. Rogue 判定四策略（任一命中即 Rogue）：① 信号强度超门限（默认 -70dBm，范围 -50~-90）；② 广播了本网配置的有效 SSID（仿冒/钓鱼）；③ SSID 名命中关键字黑名单；④ MAC OUI 命中 Rogue OUI 列表。
  3. 处置动作：Rogue Containment 默认启用——扫描 AP 向 Rogue 的关联客户端发 de-auth 反制；攻击检测（AP/Client Attack Detection）默认开启，灵敏度分 Custom/High/Medium/Low；Client Blocklist 默认关闭。
  4. 前提依赖：WIPS 依赖 AP 开启背景扫描（默认间隔 20s/时长 50ms）；扫描期间该射频无 802.11 数据，参数是安全/性能权衡。

A1 — 书中的应用 (Past Application)

案例 1: Rogue 识别与抑制全流程（p381-389）

  • 问题: 网络中发现外部 AP，如何判定危害并自动反制。
  • 方法论的使用: 按分类模型走——外部 AP 先落 Interfering；若它广播了本网合法 SSID（Detect Valid SSID 策略）或信号强于 -70dBm，则升 Rogue；Rogue Containment 自动向其关联客户端发 de-auth；WIPS Summary 查看 Rogue AP/客户端关联与 Top N Attacks。
  • 结论: 分类是策略驱动的，不是"看见外部 AP 就抓"；调门限即可控制误报/漏报。
  • 结果: 非法 AP 被自动抑制，攻击可审计。

案例 2: 友商/邻居 AP 的定性（"友商 AP 在隔壁算不算 Rogue"）

  • 问题: 隔壁公司或友商的合法 AP 被检出，客户不想被反复告警。
  • 方法论的使用: 该 AP 未命中四策略时只是 Interfering；若担心业务干扰或不想上报，按 OUI（如 ALE OUI 默认友好）或手工标记 Friendly。
  • 结论/结果: Friendly 不再以 Interfering/Rogue 上报，告警噪音消除。

A2 — 触发场景 (Future Trigger) ★

用户会在什么情境下需要这个 skill?

  1. 安全巡检发现外部 AP/私装 AP，客户问"这算不算 Rogue、要不要反制"。
  2. 出现钓鱼/仿冒 SSID（同名或近似企业 SSID），需要触发 Rogue 判定与 containment。
  3. Rogue 误报太多（把邻居/友商 AP 判成 Rogue）或漏报，需要调整四策略与 -70dBm 门限。
  4. WIPS 攻击告警处置：级别怎么选（Custom/High/Medium/Low）、要不要拉黑攻击源 MAC。
  5. 开 WIPS 前评估背景扫描对客户端性能的影响。

语言信号 (用户的话里出现这些就应激活)

  • "发现一个不明 AP / 私接的 AP / rogue AP 怎么处理"
  • "隔壁公司的 AP 被报成 Rogue 了 / 误报"
  • "有人搭了同名 SSID 钓鱼 / spoofed SSID"
  • "rogue containment / de-auth 反制是什么、默认开吗"
  • "攻击源 MAC 拉黑了怎么没用 / blocklist"

与相邻 skill 的区分

  • 与 ov-rf-tuning 的区别: RF 调优处理空口质量（信道/功率/负载/扫描参数的性能面）；本 skill 处理"外部设备的安全定性与反制"。背景扫描参数两边都涉及：性能诉求走 RF 调优，检测保真诉求归本 skill。
  • 与 ov-ssid-psk-selection 的区别: SSID 选型管自家网络安全级别；本 skill 管别家 AP 的发现与处置。仿冒 SSID 事件的"根因加固"（如换 802.1X）可衔接 SSID 选型。
  • 与 ov-device-activation-troubleshoot 的区别: 设备上线/纳管问题与 WIPS 无关。

E — 可执行步骤 (Execution)

当 skill 被激活后, agent 应按以下步骤执行:

  1. 定性目标 AP
  2. 逐条核对四策略：信号强度是否超门限（对照当前配置，默认 -70dBm）？是否广播本网有效 SSID？SSID 名是否命中关键字黑名单？MAC OUI 是否命中 Rogue OUI？输出分类结论：Interfering / Rogue / 建议标记 Friendly。
  3. 完成标准: 给出分类结论 + 命中/未命中的具体策略项。
  4. 选择处置动作
  5. Rogue → 确认 Rogue Containment（默认启用，de-auth 反制）符合客户意愿（注意反制的法律/邻居影响）；误报 → 调门限（-50~-90）、精简关键字/OUI，或将可信 AP 标记 Friendly；攻击告警 → 按需求选检测级别，攻击源是否拉黑先判断 MAC 类型。
  6. 完成标准: 处置动作明确（配置路径 + 参数值），误报类问题给出策略修正建议。
  7. 验证与评估前提
  8. 确认相关 AP 已开启背景扫描（WIPS 前提）；验证路径：WIPS Summary 看 Rogue AP/客户端关联、Blocklist、Top N Attacks；评估扫描参数对性能的影响（保持默认 20s/50ms，必要时专用扫描 AP 或 Voice/Video Awareness）。
  9. 完成标准: 输出验证方法 + 性能影响说明。

B — 边界 (Boundary) ★

不要在以下情况使用此 skill

  • 纯空口质量优化（信道冲突、吞吐、负载均衡）：走 ov-rf-tuning，发现"外部 AP 干扰"本身不等于安全事件。
  • 自家 SSID 的认证/加密加固选型：走 ov-ssid-psk-selection。
  • 有线侧准入与认证：走 ov-wired-auth-config。

作者在书中警告的失败模式

  • Blocklist 限制（ce19, p387）: 攻击源 MAC 可能是 AP MAC、BSSID 或网卡 MAC；blocklist 只对"真实无线客户端"的源 MAC 有意义（阻断的是关联行为），默认关闭，可配时效。盲目拉黑非客户端 MAC 无效果。
  • 扫描即代价（ce15, p373/376）: 扫描期间无 802.11 数据；间隔↑或时长↓ = 漏检↑但性能↑。为灵敏检测收紧扫描会伤客户端吞吐；关闭扫描即失去 WIPS。
  • Containment 是主动反制: 默认启用并向 Rogue 的客户端发 de-auth，波及邻居网络时需客户知情（书中未展开法律边界，属盲点）。

作者的盲点 / 时代局限

  • 未讨论 containment 误伤（把合法邻居网反制）的法律/合规风险；未覆盖 6GHz 频段扫描特性。

容易混淆的邻近方法论

  • Interfering（默认分类，只代表"空中可见的外部 AP"）≠ Rogue（命中策略才升级）≠ Friendly（白名单）——用户口语中"干扰 AP/非法 AP"常混称，需先按四策略定性再谈处置。

相关 skills (阶段 3 填充)

  • composes-with ov-rf-tuning: WIPS 硬依赖背景扫描（默认 20s/50ms）——扫描即代价（扫描期间无 802.11 数据）。性能权衡调参走 RF 调优，检测保真与 Rogue 判定归本 skill，高保真检测用专用扫描 AP 或 Voice/Video Awareness。
  • composes-with ov-ssid-psk-selection: 仿冒/钓鱼 SSID 事件的安全定性（升 Rogue + containment）归本 skill；根因加固（如换 802.1X、提高 SSID 安全档位）衔接选型 skill。
  • composes-with ov-mesh-bridge-rap: Auto Mesh root AP 广播的隐藏 SSID "Stellar-MESH"（5GHz）是合法行为，不是 Rogue/钓鱼——定性前先核对是否自家 Mesh，勿触发 containment 反制。
