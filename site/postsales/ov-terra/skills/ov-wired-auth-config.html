ov-wired-auth-config

SKILL 来源页码: p446-460 (Wired Client Authentication)

有线客户端认证四步配置 (OmniVista)

R — 原文 (Reading)

"[PRE] – Access Role Profiles Preconfigured / 1 – AAA Server Profile Configuration / 2 – Access Auth Profile Configuration / 3 – Access Policy Configuration / 4 – Declare Client MAC address in local database"

— ALE Training, Wired Client, p451

I — 方法论骨架 (Interpretation)

AP 下联口 / OmniSwitch 接入口上有线客户端(以 MAC 认证为例)的准入是一条四步链，外加一个前置：

  • [前置] 预配两个 Access Role Profile 并应用到 AP Group 或交换机: 受限角色(如 ARP_DEFAULT) + 全权角色(如 ARP_PASS)——角色先行，未声明 MAC 的设备落受限角色兜底。
  • 1. AAA Server Profile (Configure > Network Access > Unified Access): 选认证服务器(内置 UPAMRadiusServer) + 认证方法(MAC)。
  • 2. Access Auth Profile: 启用认证方法、绑定 AAA Profile、设默认 Access Role(=受限 ARP)、指派 AP Group 并启用物理口(AP 的 Eth1；OmniSwitch 场景则选交换机与接入口)。
  • 3. Access Policy (UPAM-NAC > Access Policies): 定义映射——条件 Authentication Type=MAC、Authentication Source=Local Database、命中角色 ARP_PASS、Web Redirection=None。
  • 4. 本地库声明: Company Property 中登记客户端 MAC(可附设备信息)，接入验证。

思维: 自下而上(服务器→端口策略→身份库)，身份命中升权、未命中由默认 ARP 兜底。支持有线认证下联口的 AP: AP1251/AP1301H/AP136x/AP1311；认证方式可 802.1X/MAC/Captive Portal。IoT 设备自动识别(MAC OUI + DHCP 指纹)可按分类自动指派 ARP，作为此流程的自动化补充。

A1 — 书中的应用 (Past Application)

案例 1: AP "Home-AP" Eth1 口接打印机 (p446-459)

  • 问题: AP 下联口(Eth1)接入的有线哑终端需准入控制。
  • 方法论的使用: 预配 ARP_DEFAULT(受限+限带宽)/ARP_PASS(全访问)挂到 AP Group "My_AP-GROUP1"，再按四步: AAA Server Profile 选 UPAMRadiusServer + MAC → Access Auth Profile 绑定并启用 Eth1、默认角色 ARP_DEFAULT → Access Policy 映射 MAC/本地库 → Company Property 登记 MAC 11:22:33:44:55:66。
  • 结论: 未知 MAC 落 ARP_DEFAULT 受限，已声明 MAC 落 ARP_PASS 全访问。
  • 结果: 打印机正常受控接入；验证入口 Device Catalog > Wired Ports 与 Analytics > Clients 看有线会话。

A2 — 触发场景 (Future Trigger) ★

用户会在什么情境下需要这个 skill?

  1. AP 下联口或 OmniSwitch 接入口要接打印机/IP 电话/摄像头等哑终端，需 MAC 准入与角色控制。
  2. 有线口未知设备要兜底受限(只能访问有限资源)，登记过的设备升全权。
  3. 客户问"哪些 AP 支持下联口认证/有线口能不能做 Portal"。

语言信号 (用户的话里出现这些就应激活)

  • "AP 下联口 / Eth1 接打印机怎么认证"
  • "有线客户端 MAC 认证 / wired client authentication"
  • "access auth profile / AAA server profile / access policy 怎么配"
  • "在本地库里声明 MAC / company property"

与相邻 skill 的区分

  • 与 ov-ssid-psk-selection 的区别: 那个是无线 SSID 的认证/密钥选型；本 skill 是有线端口准入的固定四步实操链。
  • 与 ov-policy-bandwidth-design 的区别: 那个设计 ARP/Policy List 内容与带宽；本 skill 只解决"有线口认证怎么配起来"，角色内容复用即可。

E — 可执行步骤 (Execution)

  1. 核对前置与硬件: 确认 AP 型号支持下联口认证(AP1251/AP1301H/AP136x/AP1311)或目标是 OmniSwitch 接入口；确认两个 ARP(受限兜底 + 全权)已建好并挂到 AP Group/交换机。
  2. 完成标准: 说出目标端口所属设备、将启用的物理口、两个 ARP 的名称与用途。
  3. 按四步链输出配置: ① AAA Server Profile(UPAMRadiusServer + MAC) → ② Access Auth Profile(方法+AAA Profile+默认 ARP+AP Group+物理口) → ③ Access Policy(Type=MAC、Source=Local Database、角色=全权 ARP、Web Redirection=None) → ④ Company Property 登记客户端 MAC。给出各步界面路径。
  4. 判停条件: 若客户要 802.1X/Portal 而非 MAC，调整第①③步的认证方法与重定向字段，链路结构不变。
  5. 完成标准: 四步配置清单完整，含具体对象名与端口。
  6. 验证: 接入客户端，在 Device Catalog > Wired Ports 看端口/UNP 客户端状态，Analytics > Clients 看有线会话；用一台未声明 MAC 的设备确认落受限角色。
  7. 完成标准: 已声明 MAC 落全权角色、未声明 MAC 落受限角色，两条路径均验证通过。

B — 边界 (Boundary) ★

不要在以下情况使用此 skill

  • 无线客户端认证/密钥选型 → ov-ssid-psk-selection。
  • AP/交换机本身激活纳管失败 → ov-device-activation-troubleshoot。
  • IoT 终端自动画像与分类治理(仅 3 页浅述)——本 skill 只在需要"登记 MAC 手工准入"时适用，自动分类需求另行设计。

作者在书中警告的失败模式

  • 跳过前置直接配四步: ARP 未预配/未挂到 AP Group，Access Auth Profile 无默认角色可选，链路配不完整(p451)。
  • 忘记第 4 步在本地库声明 MAC: 客户端永远落默认受限角色，误判为"认证不生效"。
  • MAC 认证固有缺陷: MAC 可仿冒、流量不加密(p215)——敏感有线网段应上 802.1X。
  • 在不支持下联口的型号(如 AP1101)上期望有线认证——先核对型号清单。

作者的盲点 / 时代局限

  • 培训示例以 MAC + 本地库为主线；外部 RADIUS/LDAP 做有线 802.1X 的字段细节需查版本文档。
  • IoT 自动识别(画像→分类→ARP enforcement)书中仅浅述，不能据此承诺完整 NAC 能力。

容易混淆的邻近方法论

  • 设备纳管的"声明序列号"(Device Catalog) vs 客户端的"声明 MAC"(Company Property)——前者管 AP/交换机上线，后者管终端准入，两个库不要混。
  • Access Auth Profile(端口认证开关) vs Access Policy(命中后给什么角色)——前者是门，后者是映射。

相关 skills (阶段 3 填充)

  • composes-with ov-ssid-psk-selection: 无线与有线准入共享同一套 UPAM 认证服务器与 Access Role Profile 体系；DSPSK 依赖的 Company Property 库同时承载有线 MAC 声明——哑终端无论无线（DSPSK）还是有线（MAC 认证）应统一角色规划。
  • composes-with ov-policy-bandwidth-design: 本 skill 只解决"有线口认证链怎么配起来"，四步命中/兜底角色（ARP_DEFAULT/ARP_PASS）的带宽与 Policy List 内容由策略设计 skill 定义。
