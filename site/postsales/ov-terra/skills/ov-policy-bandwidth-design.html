ov-policy-bandwidth-design

SKILL 来源页码: p237-289 (Unified Policies and Bandwidth Control / Client Accounts / Guest & BYOD)

统一策略分层与三层带宽合同设计 (OmniVista)

R — 原文 (Reading)

"Bandwidth contract at SSID level: per SSID and per AP, shared between all users... Bandwidth contract at Access Role Profile level: bandwidth assigned to the users using this profile... A Policy List (ACL/QoS) can restrict the bandwidth as an action."

— ALE Training, Unified Policies and Bandwidth Control, p268-269

I — 方法论骨架 (Interpretation)

用户权限与带宽由一条自底向上构建、自顶向下生效的分层链收敛：

  1. 分层模型: SSID(入口) → 认证(UPAM/RADIUS/本地库) → Access Role Profile(角色: VLAN + 默认 Policy List + 每用户带宽) → Policy List(规则集: Accept/Drop、限速、802.1p/DSCP 标记，双向执行)。配置顺序: 先建原子 Policy → 组装 Policy List → 挂到 ARP 或由 RADIUS 账号属性下发。
  2. 三层带宽合同裁决 (粗层兜底、细层收敛): 流量先匹配 Policy List ACL → 命中则按 ACL 限速(每用户每应用)；未命中看 ARP 是否设带宽(每用户)；再看 SSID 合同(该 AP 上此 SSID 全体用户共享，不是每用户)；都没有则不限速。
  3. 访客运营体系: Guest/BYOD Access Strategy 定 Login Strategy / Post Portal Enforcement / 自助注册；Registration Profile 定义配额(数据 MB + 时长)与耗尽处理(阻断或降速)；Service Level(≤5 个)把 ARP + Policy List + Registration Profile 打包成分级套餐；Guest Operator 供前台批量发号与审批。

A1 — 书中的应用 (Past Application)

案例 1: Policy-Guest 限速策略 (p263-269)

  • 问题: 访客流量需按应用放行并整体限速。
  • 方法论的使用: 先建规则 http-traffic=Accept、Network-traffic=Deny、Guest-speed=1Mb/s、Guest-priority=802.1p=3，组装为 Policy List "Policy-Guest"，挂到访客 ARP。
  • 结论: 三层合同中 ACL 级最细，命中即按 1Mb/s 执行；未命中流量回落到 ARP/SSID 级约束。
  • 结果: 访客/员工流量按三层合同精确限速。

案例 2: 访客配额 100MB/4H 超量降速 (p271-288)

  • 问题: 酒店式访客网络要求超量后降速而非断网。
  • 方法论的使用: Registration Profile 设 Data Quota 100MB + Time Quota 4H/天，Exhaustion Handling 选降速 UP=100kB/s、DOWN=1000kB/s。
  • 结论: Day1 用 90MB/3H 无动作；Day2 超 100MB 自动触发降速——"配额 + 耗尽处理"成对设计。
  • 结果: 访客超限自动降速不断网，前台可用 Guest Operator 批量发号。

A2 — 触发场景 (Future Trigger) ★

用户会在什么情境下需要这个 skill?

  1. 客户反馈"给访客/某部门限速不生效"或"用户之间互相挤占带宽"——需按三层裁决顺序排查。
  2. 设计访客网络: 门户认证方式、配额(流量/时长)、超量后阻断还是降速、分级套餐。
  3. 一套 SSID 内按角色分权分流: 不同 ARP + Policy List 组合(如员工全通、承包商限 HTTP)。

语言信号 (用户的话里出现这些就应激活)

  • "限速不生效 / bandwidth contract 不起作用"
  • "访客超流量后想降速不想踢下线 / quota exhaustion"
  • "policy list 怎么挂到角色上 / Access Role Profile 带宽"
  • "service level / registration profile / guest operator / 访客分级"

与相邻 skill 的区分

  • 与 ov-ssid-psk-selection 的区别: 那个解决"SSID + 加密 + 密钥粒度怎么选"；本 skill 解决"认证之后给多少权限和带宽"。
  • 与 ov-wired-auth-config 的区别: 那个是有线端口认证四步实操；本 skill 是策略与带宽的设计方法论(有线无线通用)。

E — 可执行步骤 (Execution)

  1. 定位层级: 确认用户诉求落在哪一层——应用级限速(Policy List/ACL)、用户级(ARP)、SSID 级共享合同、还是访客配额(Registration Profile)。
  2. 完成标准: 能说出该诉求应由哪层对象承载及理由。
  3. 自底向上构建: 按 Policy(规则) → Policy List(规则集) → ARP(角色: VLAN + 默认 Policy List + 每用户带宽) → SSID(可选共享合同) 顺序给出配置项与界面路径；访客场景补充 Access Strategy + Registration Profile(配额 + 耗尽处理成对) + Service Level(≤5)。
  4. 完成标准: 输出完整配置清单，含具体参数值(限速 kB/s 或 Mb/s、配额 MB/h)。
  5. 按裁决顺序验证: 对照三层裁决链(ACL 命中 → ARP → SSID → 不限)推演目标用户流量的实际限速结果，确认与诉求一致。
  6. 判停条件: 若推演结果不符(如 SSID 共享合同被误当每用户限速)，回到步骤 2 修正层级。
  7. 完成标准: 逐层推演结论与客户预期带宽行为一致。

B — 边界 (Boundary) ★

不要在以下情况使用此 skill

  • 纯 SSID 数量/加密/PSK 粒度选型 → ov-ssid-psk-selection。
  • 设备激活卡状态、平台部署问题 → 对应排障 skill。
  • 无线信号弱/漫游/信道调优类投诉 → ov-rf-tuning / ov-roaming-troubleshoot。

作者在书中警告的失败模式

  • SSID 级带宽合同是"每 AP 每 SSID 全体用户共享"，不是每用户限速(p268)——误当每用户用会导致用户互相挤占、投诉"限速不生效"。
  • Registration Profile 只配配额不配耗尽处理，超量行为不可预期——两者必须成对设计(p283-284)。
  • Service Level 最多 5 个(p282)，分级套餐设计超出会失败。
  • Guest 账户必填三要素: 登录名/密码、过期日期、Service Level/Registration Profile(p280)，缺一不可。

作者的盲点 / 时代局限

  • 培训书仅演示内置 UPAM 场景; 外部 RADIUS 下发 Policy List 属性时属性名/格式需查版本配套文档。
  • 带宽合同对上行/下行的分别粒度以当时版本 UI 为准。

容易混淆的邻近方法论

  • ACL 的 Drop 与限速动作 vs 防火墙安全策略——Policy List 是接入侧 QoS/访问控制，不做状态检测。
  • 访客配额降速 vs 运营商计费限速——前者按 Registration Profile 触发，与计费系统无关。

相关 skills (阶段 3 填充)

  • composes-with ov-ssid-psk-selection: SSID/密钥选型决定"进门身份"，本 skill 决定"进门后多少权限和带宽"——分层链 SSID→认证→ARP→Policy List 的前半段由选型 skill 定，ARP 内容与 Policy List 由本 skill 设计。
  • composes-with ov-wired-auth-config: 有线认证四步链只管"端口认证怎么配起来"，其命中/兜底角色的 ARP 内容（VLAN、默认 Policy List、每用户带宽）复用本 skill 的设计方法论——有线无线通用。
